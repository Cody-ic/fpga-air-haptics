# FPGA 工程：串口接收通路

更新日期：2026-09-25。

本目录存放 FPGA 侧的 RTL（Register Transfer Level，寄存器传输级，即用代码描述电路）。**整条链路已经接通并且端到端仿真通过**：电脑发来的 HAP3 报文收进来、校验 CRC（Cyclic Redundancy Check，循环冗余校验）、解析字段、裁决命令，带多段草图的配置会先解析成点表、再编译成「节拍表」，START 之后走步器每 10 µs 走一步输出焦点坐标，同时板子把应答（ACK / ERR / 状态快照，含原样的 `scan_paths`）发回去，每 500 毫秒还会主动上报一份状态，免得上位机判超时。相位计算和输出级还没有。

> 文件名里的 `hap2_` 是历史命名，内容已经升级到 HAP3。改名是纯机械操作，等接口稳定后再一起做。

协议规格见 [desktop_app/PROTOCOL.md](../desktop_app/PROTOCOL.md)，第 7 节是固件侧实现要点。

## 怎么跑仿真

先在仓库根目录生成向量（需要 Python 3.10+ 和 `desktop_app/requirements.txt` 里的依赖）：

```powershell
python fpga/tb/gen_vectors.py
```

然后在装有 Verilator 的环境里编译并运行。必须在 `fpga/` 目录下运行，因为测试台用相对路径读向量文件：

```bash
cd fpga
bash tb/run_verilator.sh
```

默认在 `$HOME/.cache/hap2_sim` 下编译，不往仓库里塞编译产物；可用 `BUILD_DIR=...` 覆盖。

## 仿真覆盖了什么

- **CRC 自检**：对 `"123456789"` 算，结果必须是 `29B1`（协议里的参考向量）
- **七个整帧级用例**：带 CRLF 的握手命令、只有 LF 的探活命令、被改坏的校验码、没有星号的行、星号后校验码不足的行、真实的 240 字节配置命令、以及字节之间带空档的同一命令
- **行长检查**：逐个核对剥掉 CR 之后的行长
- **十个字段级用例**：标准配置命令（16 个字段齐全、数值抽查）、重复字段、载波越界、值里有非法字符、缺少必填字段、多一个不认识的键、不认识的命令、握手与探活这类无字段命令、三角形预设的图形名识别
- **错误分类检查**：每个失败用例都要报出正确的错误码（重复键 4、非法字符 3、越界 6、缺字段 8），并且**第一个错就停**，不再继续解析后面的字段
- **十八个命令级用例**：完整走一遍权限矩阵——没握手就发配置、握手、配置生效、阵列不符被拒、探活、切本地、本地控制下改配置／启动被拒、切回远程、启动、重复启动报忙、暂停、重复暂停报未运行、恢复、停止、要状态、不认识的命令、配置越界。每个用例都核对**应答类型、错误码、控制模式、运行状态、配置版本号、要不要跟状态、应答里的序号是否原样抄回**
- **配置是否真的落地**：抽查替换后的载波、等级、图形编号
- **心跳失联**：运行中模拟主机失联，应当自动回到待机并记下原因码
- **板子发出来的报文逐字节对照**：测试台用一个串口接收器接住板子的发送线，把收到的字节和 Python 参考实现生成的期望报文逐字节比对（含校验码）。覆盖握手应答（346 字节，含完整能力声明）、配置应答、拒绝应答
- **状态快照**：核对帧内校验码、开头格式，以及 `state=`、`carrier_hz=`、`shape=`、整张相位串是否都正确
- **看门狗**：启动后主机停止发报文，板子应当在心跳超时后自己回到待机并记下原因码；反面用例验证主机按时探活时不会被误停
- **应答撞车**：板子正在发长应答时，主机又发来一条命令（上位机每 0.8 秒一次探活，撞上概率约 8%）。两条应答都必须发出去，一条都不能丢
- **多段草图解析**：单段、两段、负坐标要能正确解析出点表和段表；相邻点重合、空段、坐标越界、缺横坐标、非法字符、点数超 256 都要被**拒绝**（不是截断）
- **算术单元（单独的测试台）**：整数开方与无符号除法。开方覆盖 0、1、完全平方数、典型的两轴／三轴平方和、42 位最大值；除法覆盖整除、有余数、商为 0、以及除数为 0 的拒绝路径
- **轨迹通路（单独的测试台）**：八个用例，两类检查。**节拍表逐行**核对拍数、x/y 步进、扫描开关、笔号（期望值由 `gen_vectors.py` 照协议规则独立算一遍）；**每拍焦点**与 `desktop_app/model.py` 的参考实现逐拍对拍（含扫描开关和笔号，每 13 拍取一个样本、换行点前后加密）。覆盖两笔草图、闭环方框、单点笔（原地停留）、两笔各 20 µm 的短笔画（触发 0.1 mm 最低权重）、8 点 2 笔的碎图形，以及三条拒绝路径：抬笔时间占满一圈、一圈塞不下、图形碎到 1 µm 的小段分不到一拍。实测位置偏差最大 1 个 0.5 µm 单位（碎图形那一路是 19 个，因为一小段只分到几拍，挪一拍就差这么多，容差里已经算进去了）
- **端到端（单独的测试台，`tb_hap2_top.v`）**：把 `hap2_top` 当成一块真板子，只碰串口线和几个输出引脚。按顺序发 12 条真实报文：握手（核对应答里声明了 `SCAN_PATHS`）→ 发一份两笔草图（核对 ACK、版本号 +1、STATE 里 `scan_paths` 原样回传、`scan_on=0`）→ 启动（核对 `state=RUNNING`，并且真的走：8 毫秒里数到扫描 2000 拍、抬笔 400 拍、走到第 1 笔、焦点从 2000 挪到 22000）→ 暂停（焦点冻住、输出关掉）→ 恢复（接着走，不是回到起点）→ 停止（回到起点 (2000,4000)、扫描开关和输出都关）→ 发一份碎到做不出节拍表的图形（核对 ERR `BAD_CONFIG`、版本号不动、回传的草图原文也没被污染）→ 要状态 → 发预设图形（核对 `scan_paths=NONE`）→ 启动（预设图形没有轨迹，焦点原地不动）→ 停止 → 探活（只回一条 ACK，不跟状态）。输出使能的三个条件（运行中 + 等级>0 + 正在扫描）在每一个节拍上都核对一遍
- **超长丢弃**：用小上限实例验证「正文满上限后整行丢弃」这段逻辑
- **串口层自查**：解出来的字节数与发出去的一致，且没有帧错

最后一条很关键：**逐通道比对用的是 `desktop_app` 里那份参考模型生成的真实报文**，不是手抄的字节，所以不存在抄错的可能。

## HAP3 声明了哪些能力

固件在 HELLO 应答里声明 `caps=CONFIG,MODE,START,PAUSE,STOP,STATE,PHASE,SCAN_PATHS`。

`SCAN_PATHS` 是这一轮才加上的：多段草图从「收到文本」到「按节拍走出焦点」整条路都通了、也端到端仿真过了，才敢声明。上位机会按能力声明决定发什么——`controller.py` 里对 `scan_paths != NONE` 的配置会先查这个能力，没声明就不发。

仍然**不声明 `CUSTOM_XY`**（`path_xy_um` 旧点列还没解析），所以上位机不会发那种配置过来。预设图形（CIRCLE 等）不需要声明，但固件目前只是接受配置、没有对应的轨迹，启动后焦点原地不动、`scan_on` 保持 0——这一块要等相位计算那一轮补。

容量字段照常声明（`max_nodes=64`、`max_scan_points=256`、`max_strokes=32`）。

## 应答是怎么组装出来的

`hap2_tx.v` 把四种报文写成「模板字符串」，模板里用特殊符号当占位符：

| 占位符 | 展开成 |
|---|---|
| `@` | 一个十进制数 |
| `#` | 4 位十六进制校验码 |
| `+` | 8 位十六进制启动标识 |
| `~` `^` `%` `&` `$` `!` | 命令名、错误码名、控制模式、运行状态、图形名、停止原因 |
| `\|` | 整张相位表（逗号分隔） |

发的时候逐字符扫模板：普通字符直接发，占位符就去生成对应内容。**协议要加字段时改模板就行，不用动状态机。**

校验码是边走边算的：每发一个正文字节就喂给 CRC 模块，遇到星号停止累加，星号后面四位就是算出来的值。注意**星号、换行、以及校验码自己这四位不算正文**，其余都要算进去。

## 为什么应答要排队

一条应答加一份状态帧有 460 字节，串口要发 **40 毫秒**（配置命令是 417 字节，更久）。而上位机每 **0.8 秒**发一次探活命令——撞上这 40 毫秒窗口的概率约 8%。

如果不排队，板子正忙时来的命令应答就被丢掉了，上位机等 2 秒收不到回应就会断开连接。`hap2_tx.v` 里因此放了一个深度 4 的队列：发不完的先排队，发完手上的接着发，**不丢**。队列真的满了才丢，并记在 `drop_cnt` 里（正常情况下应当是 0）。

## 命令裁决是怎么做的

`hap2_cmd.v` 把八条命令和各自的允许条件写成一张表，一帧解析完就按表判定：

| 命令 | 允许条件 | 被拒时的错误码 |
|---|---|---|
| `HELLO` | 任何时候 | — |
| `PING` | 握手后 | `HANDSHAKE_REQUIRED` |
| `CONFIG` | 握手后 + 电脑控制 + 待机 | `LOCAL_CONTROL` / `BUSY` / `HARDWARE_MISMATCH` |
| `MODE` | 握手后 + 待机，且带 `value=LOCAL/REMOTE` | `BUSY` / `BAD_MODE` |
| `START` | 握手后 + 电脑控制 + 待机或暂停 | `LOCAL_CONTROL` / `BUSY` |
| `PAUSE` | 握手后 + 电脑控制 + 运行中 | `LOCAL_CONTROL` / `NOT_RUNNING` |
| `STOP` | 握手后，两种模式都行 | — |
| `SNAP` | 握手后 | — |
| 其它 | — | `UNKNOWN_COMMAND` |

配置用**影子寄存器 + 一次性替换**：字段流先写进影子，阵列核对、范围检查全部
通过，才整体拷进生效寄存器并把 `rev` 加一。任何一步不过就原样保留旧配置，
不会出现「换了一半」的中间状态。

## 这几块是怎么接起来的（`hap2_top.v`）

```text
串口线 → 收字节 → 攒成一整行 → 校验码 → 解析字段 ─┬→ 命令裁决（hap2_cmd）
                                                  │     ├→ 草图子系统（hap2_traj_scan）
                                                  │     │    文本 → 点表/段表 → 节拍表 → 走步器
                                                  │     └→ 应答组装（hap2_tx）→ 串口线
                                                  └→ 心跳看门狗（hap2_watchdog）
```

行缓冲只有一块，读口按「谁在跑就让给谁」排队：CRC 校验 → 字段解析 → 草图解析。
三段本来就是串着走的（前一段完了才轮到下一段），所以不冲突。

接线时有四个地方值得记下来：

**1. 带草图的 CONFIG，ACK 要等节拍表算完才回。** 协议里 `ACK applied=1` 的意思就是
「这份配置已经生效」，而能不能生效要等节拍表算出来才知道（碎到做不出的图形必须回
`BAD_CONFIG`）。所以命令层里多了一个「待办配置」的小状态机：收到 CONFIG →
解析原文 → 编译节拍表 → 通过了才整体替换配置、`rev` 加一、回 ACK + STATE；
任何一步不过就回 ERR，配置一个字都不动。这段要花大约 1 毫秒，期间电脑正常只会发探活，
探活照常回 ACK，别的命令先回 `BUSY`。

**2. 走步器的启停跟着运行状态走。** START（从待机）→ 从轨迹起点重新开始；
START（从暂停）→ 解开冻结、接着走（不是回到起点）；PAUSE → 冻结位置、输出关闭；
STOP 或心跳超时 → 停下并回到起点。另外命令层记着一个 `traj_ready`：没有可用节拍表时
（比如刚发的是预设图形），START 只把状态改成 RUNNING，不启动走步器——
免得把上一份图形的表当成这一份接着走。

**3. STATE 里的 `scan_paths` 必须原样回传。** 上位机收到状态帧后会拿里面的字段重建
配置对象并校验（`Config.from_wire` 会检查「CUSTOM 图形必须有坐标」），所以草图文案
不能糊弄。行缓冲下一帧就被覆盖了，所以草图子系统在解析的同时把原文抄进一块 8 KB 的
缓冲（上下两半各 4 KB）：解析写「没在对外的」那一半，配置被接受了才把对外的那一半
切过去——只翻一个指针，不搬字节；被拒绝的配置也就污染不了回传内容。

**4. 板子要主动上报状态。** 上位机每 0.8 秒发一次探活、只收到 ACK，而状态超过 2.5 秒
没到就判过期、随后断开。所以顶层加了一个计时器，每 500 毫秒（`STATE_MS` 参数，
测试台里设 0 关掉）往发送队列里插一份状态快照。草图很长时一帧状态本身就要几百毫秒，
那时可以把间隔调大。

## 轨迹是怎么走的（节拍表 + 走步器）

这里说的「节拍」是**焦点什么时候走到哪里**，跟「时序优化」里的时序（信号能不能在一个
时钟周期内稳定下来）是两回事。

整条路分成两半，中间用一张表隔开：

| 阶段 | 什么时候干 | 干什么 | 花多少时间 |
|---|---|---|---|
| `hap2_traj_plan` | 收到 CONFIG、机器停着 | 开方算段长、除法分配拍数，写出一张节拍表 | 约 1 毫秒（几百微秒到 1 ms，反正串口收一条 CONFIG 本身就要 100 ms） |
| `hap2_traj_walk` | START 之后一直在跑 | 每 10 µs 在定点累加器上加一次步进，输出焦点坐标 | 每拍 500 个时钟（50 MHz），里面只有加减法 |

节拍表的一行 = 一段**匀速直线移动**，四个字段：走多少拍、每拍 x 走多少、每拍 y 走多少、
这一段是扫描（`scan=1`）还是抬笔跳转（`scan=0`）；另外带一个「这是第几笔」。表按时间顺序
排好，最后一笔的跳转段回到第一笔的首点，于是整圈闭环。

拍数怎么分（照抄参考实现 `desktop_app/model.py` 的 `trajectory_sample()`）：

```text
一圈拍数   laps  = 10^8 ÷ repeat_millihz          （一拍 10 µs）
抬笔跳转   blank = blank_us ÷ 10                  拍
可扫描     active = laps − 笔数 × blank           （必须 > 0）
每笔权重   weight = max(该笔路径总长, 0.1 mm)      ← 协议明文规定
每笔拍数   = active × weight ÷ Σweight
笔内每段   = 该笔拍数 × 段长 ÷ 该笔总长
每拍步进   = |dx| × 2^16 ÷ 该段拍数                （定点数，低 16 位是小数）
```

分配拍数时**每次除法的余数带到下一次分配里**，而不是各自四舍五入。这样
`Σ每段拍数 = active` 一拍不差，一圈正好 `laps` 拍，长期跑也不会慢慢偏。

三种情况会**整份拒绝**（保留上一份配置，回 `BAD_CONFIG`）：

1. 协议里显式写的 `blank_us × 笔数 × repeat_millihz ≥ 10^9`（一秒里的抬笔时间装不下）；
2. 一圈塞不下这么多抬笔（`laps ≤ 笔数 × blank`）；
3. 某个小段连**一拍**都分不到。10 µs 的节拍追不上这么碎的图形，与其偷偷把它拉长
   （那样一圈的拍数就对不上了），不如当面拒绝，让上位机降低重复频率或简化图形。

两个踩过的坑，写在这里免得下次再犯：

- **同步读要等两拍。** 点表和节拍表都是「给地址后一拍出数据」的寄存器读口。但这「一拍」
  是相对**数据寄存器采样那一刻**说的：程序在这一拍把地址写进寄存器，地址下一拍才
  真正输出，数据再下一拍才出来。所以状态机里每次取点都要多一个空等状态
  （`S_P1_WAIT`、`S_P2_BLKB`、走步器里的 `pf` 从 1 数到 2）。
- **同一拍别用刚赋值的寄存器。** 算抬笔跳转段的 x 步进时，如果在给 `blk_dx` 赋值的那一拍
  就拿它去做除法，用到的是**上一段**的旧值（仿真里表现为第一段跳转的 x 步进是 0）。
  改成用组合逻辑算出来的当前差值就没问题了。

资源占用（Tang Mega 60K 一点都不紧张）：点表 256×21×2 ≈ 10.5 Kbit；第一趟的中间表
256×(32+32+32) ≈ 24 Kbit；节拍表 288×95 ≈ 27 Kbit。开方和除法各一套，
配置阶段分时复用（一圈最多 800 多次除法，每次 56 拍）。

## 字段解析是怎么认出键名的

`hap2_field_parse.v` 里有一张键名表，每个键名是一个 128 位的常量，
键名放在低位、左边补零。解析时每来一个字符就把缓冲整体左移 8 位、把新字符
放到最右边，攒完整个键名后与 16 个常量整体比较，一下就问出「这是哪个字段」。
这个做法顺带保证了键名长度必须完全相等——补的零不可能被键名字符匹配上。

数组下标是 `[ADDR_W-1:0]`，所以 `ADDR_W` 必须满足 `2^ADDR_W >= MAX_LINE`。

测试台里有个 `DEBUG` 开关（默认关）。把它改成 1，仿真会打印每一个解析出来的
字段（编号、类型、数值、枚举）以及每个判错的整帧，排查问题时很有用。

## 上板时要补的东西

1. 在高云 EDA 里新建工程，加入 `rtl/` 下的 `.v` 文件，顶层用 `hap2_rx`。
2. 按实际板卡原理图绑定时钟与串口引脚，并写时序约束。
3. `CLK_HZ` 参数必须填成板上的实际时钟频率（50 MHz 对应分频 434，100 MHz 对应 868）。
4. 上板前先在 Gowin 自带的仿真器里跑一遍同一套测试台，确认工具链理解一致。

## 与其他部分的关系
