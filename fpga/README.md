# FPGA 工程：串口接收通路

更新日期：2026-09-25。

本目录存放 FPGA 侧的 RTL（Register Transfer Level，寄存器传输级，即用代码描述电路）。**收发两侧都通了**：把电脑发来的 HAP3 报文收进来、校验 CRC（Cyclic Redundancy Check，循环冗余校验）、解析字段、裁决命令，再把应答（ACK / ERR / 状态快照）组装成 ASCII 文本发回去。相位计算、轨迹输出和多段草图还没有。

> 文件名里的 `hap2_` 是历史命名，内容已经升级到 HAP3。改名是纯机械操作，等接口稳定后再一起做。

协议规格见 [desktop_app/PROTOCOL.md](../desktop_app/PROTOCOL.md)，第 7 节是固件侧实现要点。

## 目录结构

```text
fpga/
  rtl/
    uart_rx.v           串口接收：115200 8N1，位中点采样
    hap2_line_rx.v      行组装：攒到 LF、剥行末 CR、超长整行丢弃
    crc16_ccitt.v       CRC16-CCITT-FALSE 计算单元
    hap2_frame_check.v  一帧的格式与 CRC 检查
    hap2_field_parse.v  帧头与字段解析：认键名、查重复、换算数值、查范围
    uart_tx.v           串口发送：115200 8N1
    dec_ascii.v         二进制转十进制 ASCII（双 dabble 算法）
    hap2_cmd.v          命令裁决：权限判断、错误码、配置影子与原子替换
    hap2_tx.v           应答组装与发送：四种报文的模板与占位符替换
    hap2_watchdog.v     主机心跳看门狗：电脑不在了就自己停下来
    hap2_rx.v           接收通路顶层（三段串行 + 行缓冲读口仲裁）
  tb/
    tb_hap2_rx.v        仿真测试台
    gen_vectors.py      用 desktop_app.protocol 生成真实报文向量
    run_verilator.sh    一键编译并运行仿真
    vectors/            生成出来的向量文件（已提交，便于复现）
```

## 怎么跑仿真

先在仓库根目录生成向量（需要 Python 3.10+ 和 `desktop_app/requirements.txt` 里的依赖）：

```powershell
python fpga/tb/gen_vectors.py
```

然后在装有 Verilator 的环境里编译并运行。必须在 `fpga/` 目录下运行，因为测试台用相对路径读向量文件：

```bash
cd fpga
bash tb/run_verilator.sh
```

默认在 `$HOME/.cache/hap2_sim` 下编译，不往仓库里塞编译产物；可用 `BUILD_DIR=...` 覆盖。

## 仿真覆盖了什么

- **CRC 自检**：对 `"123456789"` 算，结果必须是 `29B1`（协议里的参考向量）
- **七个整帧级用例**：带 CRLF 的握手命令、只有 LF 的探活命令、被改坏的校验码、没有星号的行、星号后校验码不足的行、真实的 240 字节配置命令、以及字节之间带空档的同一命令
- **行长检查**：逐个核对剥掉 CR 之后的行长
- **十个字段级用例**：标准配置命令（16 个字段齐全、数值抽查）、重复字段、载波越界、值里有非法字符、缺少必填字段、多一个不认识的键、不认识的命令、握手与探活这类无字段命令、三角形预设的图形名识别
- **错误分类检查**：每个失败用例都要报出正确的错误码（重复键 4、非法字符 3、越界 6、缺字段 8），并且**第一个错就停**，不再继续解析后面的字段
- **十八个命令级用例**：完整走一遍权限矩阵——没握手就发配置、握手、配置生效、阵列不符被拒、探活、切本地、本地控制下改配置／启动被拒、切回远程、启动、重复启动报忙、暂停、重复暂停报未运行、恢复、停止、要状态、不认识的命令、配置越界。每个用例都核对**应答类型、错误码、控制模式、运行状态、配置版本号、要不要跟状态、应答里的序号是否原样抄回**
- **配置是否真的落地**：抽查替换后的载波、等级、图形编号
- **心跳失联**：运行中模拟主机失联，应当自动回到待机并记下原因码
- **板子发出来的报文逐字节对照**：测试台用一个串口接收器接住板子的发送线，把收到的字节和 Python 参考实现生成的期望报文逐字节比对（含校验码）。覆盖握手应答（346 字节，含完整能力声明）、配置应答、拒绝应答
- **状态快照**：核对帧内校验码、开头格式，以及 `state=`、`carrier_hz=`、`shape=`、整张相位串是否都正确
- **看门狗**：启动后主机停止发报文，板子应当在心跳超时后自己回到待机并记下原因码；反面用例验证主机按时探活时不会被误停
- **应答撞车**：板子正在发长应答时，主机又发来一条命令（上位机每 0.8 秒一次探活，撞上概率约 8%）。两条应答都必须发出去，一条都不能丢
- **超长丢弃**：用小上限实例验证「正文满上限后整行丢弃」这段逻辑
- **串口层自查**：解出来的字节数与发出去的一致，且没有帧错

最后一条很关键：**逐通道比对用的是 `desktop_app` 里那份参考模型生成的真实报文**，不是手抄的字节，所以不存在抄错的可能。

## HAP3 声明了哪些能力

固件在 HELLO 应答里声明 `caps=CONFIG,MODE,START,PAUSE,STOP,STATE,PHASE`，**暂时不含 `CUSTOM_XY` 和 `SCAN_PATHS`**。

这是刻意的：上位机会按能力声明决定发什么——`controller.py` 里对 `scan_paths != NONE` 的配置会先查 `SCAN_PATHS` 这个能力，没声明就不发。上位机联调计划里也写着「不得声明未实现的路径能力」。多段草图的轨迹语义做完之前不声明 `SCAN_PATHS`，避免收了配置却做不出对应输出。

容量字段仍然照常声明（`max_nodes=64`、`max_scan_points=256`、`max_strokes=32`），它们只表示「假如支持，能收多少」。

## 应答是怎么组装出来的

`hap2_tx.v` 把四种报文写成「模板字符串」，模板里用特殊符号当占位符：

| 占位符 | 展开成 |
|---|---|
| `@` | 一个十进制数 |
| `#` | 4 位十六进制校验码 |
| `+` | 8 位十六进制启动标识 |
| `~` `^` `%` `&` `$` `!` | 命令名、错误码名、控制模式、运行状态、图形名、停止原因 |
| `\|` | 整张相位表（逗号分隔） |

发的时候逐字符扫模板：普通字符直接发，占位符就去生成对应内容。**协议要加字段时改模板就行，不用动状态机。**

校验码是边走边算的：每发一个正文字节就喂给 CRC 模块，遇到星号停止累加，星号后面四位就是算出来的值。注意**星号、换行、以及校验码自己这四位不算正文**，其余都要算进去。

## 为什么应答要排队

一条应答加一份状态帧有 460 字节，串口要发 **40 毫秒**（配置命令是 417 字节，更久）。而上位机每 **0.8 秒**发一次探活命令——撞上这 40 毫秒窗口的概率约 8%。

如果不排队，板子正忙时来的命令应答就被丢掉了，上位机等 2 秒收不到回应就会断开连接。`hap2_tx.v` 里因此放了一个深度 4 的队列：发不完的先排队，发完手上的接着发，**不丢**。队列真的满了才丢，并记在 `drop_cnt` 里（正常情况下应当是 0）。

## 命令裁决是怎么做的

`hap2_cmd.v` 把八条命令和各自的允许条件写成一张表，一帧解析完就按表判定：

| 命令 | 允许条件 | 被拒时的错误码 |
|---|---|---|
| `HELLO` | 任何时候 | — |
| `PING` | 握手后 | `HANDSHAKE_REQUIRED` |
| `CONFIG` | 握手后 + 电脑控制 + 待机 | `LOCAL_CONTROL` / `BUSY` / `HARDWARE_MISMATCH` |
| `MODE` | 握手后 + 待机，且带 `value=LOCAL/REMOTE` | `BUSY` / `BAD_MODE` |
| `START` | 握手后 + 电脑控制 + 待机或暂停 | `LOCAL_CONTROL` / `BUSY` |
| `PAUSE` | 握手后 + 电脑控制 + 运行中 | `LOCAL_CONTROL` / `NOT_RUNNING` |
| `STOP` | 握手后，两种模式都行 | — |
| `SNAP` | 握手后 | — |
| 其它 | — | `UNKNOWN_COMMAND` |

配置用**影子寄存器 + 一次性替换**：字段流先写进影子，阵列核对、范围检查全部
通过，才整体拷进生效寄存器并把 `rev` 加一。任何一步不过就原样保留旧配置，
不会出现「换了一半」的中间状态。

## 字段解析是怎么认出键名的

`hap2_field_parse.v` 里有一张键名表，每个键名是一个 128 位的常量，
键名放在低位、左边补零。解析时每来一个字符就把缓冲整体左移 8 位、把新字符
放到最右边，攒完整个键名后与 16 个常量整体比较，一下就问出「这是哪个字段」。
这个做法顺带保证了键名长度必须完全相等——补的零不可能被键名字符匹配上。

数组下标是 `[ADDR_W-1:0]`，所以 `ADDR_W` 必须满足 `2^ADDR_W >= MAX_LINE`。

测试台里有个 `DEBUG` 开关（默认关）。把它改成 1，仿真会打印每一个解析出来的
字段（编号、类型、数值、枚举）以及每个判错的整帧，排查问题时很有用。

## 上板时要补的东西

1. 在高云 EDA 里新建工程，加入 `rtl/` 下的 `.v` 文件，顶层用 `hap2_rx`。
2. 按实际板卡原理图绑定时钟与串口引脚，并写时序约束。
3. `CLK_HZ` 参数必须填成板上的实际时钟频率（50 MHz 对应分频 434，100 MHz 对应 868）。
4. 上板前先在 Gowin 自带的仿真器里跑一遍同一套测试台，确认工具链理解一致。

## 与其他部分的关系

`tb/gen_vectors.py` 直接调用 `desktop_app.protocol` 生成报文，所以**协议一旦改动，向量必须重新生成**，否则仿真测的是一份过期的格式。相位黄金向量由 `desktop_app/golden.py` 导出，属于另一条线（相位计算），暂未接入本目录。
